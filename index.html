Decisions

Why I built things the way I did

Short notes on real engineering decisions: the context, what I chose, the result, and the trade-off I accepted.

Keeping claim pages fast with caching and on-demand fax loading

Context
Opening a claim took about 20 seconds. The cause was the fax API, because the RingCentral fax API was slow to respond, and every claim page called it on load, even when the user never opened the fax tab.
Goal
Claim details should open without waiting on fax data, and the fax API should only be called when someone actually needs it.
Decision
Load the other claim details first, and call the fax API only when the Fax tab is clicked. Cache the fax responses in Redis so repeat views don't call RingCentral again.
Result
Claim details now open in about 2 seconds, down from about 20, and unnecessary fax requests are avoided.
Trade-off
Fax content appears a moment later the first time the tab is opened, so the loading state has to be clear. Cached fax data can also go stale, so it needs an expiry rule.

Keeping the database free for a complex audit job

Context
I built an automated background job that audits claims processed by about 100 employees across two shifts. The claims span 14 pools and roughly 8 workflow types, with more than 1,000 claims per employee. The audit percentage is dynamic and depends on what each employee processed, using 10 to 12 complex conditions and filters. The single query was too heavy to load at first.
Goal
Produce correct audit results first, then keep the database free so the job doesn't slow down live claim processing.
Decision
Get the output right first, then add caching, then move the filtering into C# and use Dapper to pull only the data the job needs. Last, tune the SQL so the database does less work. All filtering now runs on the server.
Result
The audit job now finishes in about 3 seconds, down from about 1 minute, without overloading the database.
Trade-off
More of the work now happens in the application, so it uses more memory and CPU on the server. The filtering rules also have to stay in step with the business rules.

Automating releases with Azure DevOps

Context
Releases were slow and depended on manual steps, so each deployment took longer than it should.
Decision
Set up the standard Azure DevOps structure: source control in Azure Repos, build artifacts from every build, and approval gates before each deployment.
Result
Deployment time dropped from 45 minutes to 18 minutes, about 60% faster.
Trade-off
The pipelines need upkeep as the project changes, and slow or flaky tests affect every release.

Role-based access for a multi-client internal platform

Context
I built internal software for multiple clients, with an 8-level hierarchy. Each level needs to see only its own portal.
Decision
Users sign in through Microsoft authentication, and a role is assigned to each user. The role decides which portal they can open and what they can do inside it.
Result
Each person signs in once with their Microsoft account and lands in the portal that matches their role.
Trade-off
With eight levels, the role design takes careful planning, and roles must be updated whenever the hierarchy changes.
